# internal/engine/coraza

Реализация интерфейса `internal/engine` на [Coraza v3](https://github.com/corazawaf/coraza) —
референсная и единственная на старте, по рекомендации
`docs/research/seclang-engines.md`: отсутствие
катастрофического бэктрекинга (RE2 вместо PCRE2), безопасность памяти при разборе недоверенного
ввода, тот же язык, что у остального референсного скелета инспектора.

Обязательные настройки движка на продакшене, все — из
modsecurity-inspector.md#правила-и-их-жизненный-цикл (`docs/research/modsecurity-inspector.md`):

- `SecRuleEngine DetectionOnly` (или CRS без финального `deny`) — решение принимает модуль по своим
  порогам, а не движок; `deny` инспектор оставляет для находок, не зависящих от счёта.
- `SecAuditEngine Off` — свой аудит уходит в JetStream, второй источник правды на диске не нужен.
- `SecDebugLogLevel 0` — не только из-за объёма: в libmodsecurity включённый лог был источником
  гонок в многопоточном режиме; для Coraza это тем не менее остаётся значением по умолчанию для
  паритета конфигурации между возможными реализациями.

Набор правил загружается из `profiles/http/` -- фазы 1-5 одним набором, обе стороны транзакции.
Он собирается целиком при старте и при сигнале перезагрузки, атомарно подменяется указателем;
запросы, использующие старый набор, дорабатывают на нём. Загрузка в уже используемый набор — не
делается никогда, это и есть источник известных падений в других реализациях SecLang.

Выбор профиля по тегу `route.profile` из сообщения делает `internal/rules`, этот пакет получает уже
выбранный набор.
