# internal/queue

Admission control. Ни libmodsecurity, ни Coraza не дают отменить идущую оценку правил, поэтому
проверка бюджета возможна только на входе, до начала работы: приём сообщений в одном потоке,
оценка — в пуле воркеров с очередью ограниченной глубины.

Две точки проверки, обе обязаны отвечать, а не отбрасывать сообщение молча:

1. **На входе в очередь.** Сообщение уже снято с шины. Прокисшие выкидываем из
   буфера (`MODSEC_DEADLINE_EXCEEDED`), чтобы слот занял свежий запрос. Если
   очередь полна *живыми* — `queue_full drop` отвечает `allow` с
   `reason.code = MODSEC_QUEUE_LIMIT` (решает модуль); `wait` держит уже снятое
   сообщение до места или до истечения бюджета.
2. **На выходе из очереди, перед вызовом движка.** `budget = deadline_ms − время_в_очереди − reserve`.
   Если `budget < min_budget` — работа не начинается вообще, ответ
   (`reason.code = MODSEC_DEADLINE_EXCEEDED`) уходит немедленно, дорогая оценка не тратится на то,
   что уже не успеет.

Опорный псевдокод обоих переходов — в
docs/research/modsecurity-inspector.md#дедлайн-латентность-и-отказ (`docs/research/modsecurity-inspector.md`);
реализация этого пакета следует ему буквально, включая источники констант `reserve` и `min_budget`
из `internal/config`.

Глубина очереди — не круглое число, а результат расчёта из целевой латентности и пропускной
способности (см. «Сайзинг по процессору» (`docs/research/modsecurity-inspector.md`)).
Оба случая отбраковки инкрементируют отдельные счётчики (`shed`, `expired`), которые нужны для
сайзинга ещё до того, как появится `waf_status` на стороне модуля.
